# bizradar: analyze/match job이 매번 실패하던 이유

## 문제 상황

bizradar의 analyze와 match job이 실행될 때마다 조용히 실패하고 있었습니다. 로그를 보니 추출 호출마다 "no 'response' field" 에러가 반복적으로 찍히고 있었고, match_scores 테이블도 한동안 갱신되지 않은 상태였습니다. 두 job 모두 각자 다른 이유로 매번 죽고 있었던 겁니다.

## 원인 추적: Ollama 응답 필드

먼저 ollama_provider부터 살펴봤습니다. 구조화된 `format` 출력을 요청했을 때 qwen3.5:9b 모델이 JSON 전체 답변을 `thinking` 필드에 넣어버리고 정작 `response` 필드는 비워두는 걸 확인했습니다. 그래서 코드에서는 `response` 필드가 없다고 매번 에러를 던졌던 것이고, 결국 모든 추출 호출이 실패하고 있었던 거였습니다. 이 부분은 실제로 라이브 환경에서 재현하며 검증했습니다.

## 원인 추적: match_scores 요청 크기

match_scores 쪽은 좀 더 골치 아팠습니다. project_analyses가 쌓이면서 opportunities_current를 조회할 때 분석된 opportunity id 전체를 `.in_()` 조건 하나에 담아 GET 요청을 보내고 있었는데, 행 수가 늘어나면서 요청 URL이 너무 커져 Supabase 게이트웨이에서 plain-text 400으로 그냥 거부당하고 있었습니다. 이 때문에 match_job은 사실상 실행될 때마다 실패하고 있었고, 회사와 공고를 매칭하는 핵심 지표인 match_scores가 거의 3주 가까이 전혀 재계산되지 않고 있었던 상태였습니다.

## 해결 과정

ollama_provider에서는 `/api/generate` 요청에 `think=false`를 명시적으로 보내도록 수정했습니다. 이렇게 하면 모델이 thinking 필드로 답을 새지 않고 `response` 필드에 제대로 결과를 채워주는 걸 확인했습니다. match_scores 쪽은 id 리스트를 통째로 보내는 대신 청크 단위로 나눠서 여러 번 요청을 보내도록 바꿨고, 이로써 URL 크기 문제를 피할 수 있었습니다.

추가로 match_job에는 회사/공고 쌍 단위로 스코어링 실패를 격리하는 로직을 넣었습니다. 하나의 쌍에서 문제가 생겨도 전체 배치가 멈추지 않고 나머지는 계속 처리되도록 만든 것입니다. 수정 후 실제 프로덕션 Supabase에 대고 검증했고, 201 응답과 함께 match_scores에 정상적으로 데이터가 들어가는 것과 job이 깨끗하게 끝나는 것까지 확인했습니다.
