반응형 웹을 처음 구현할 때는 보통 Desktop과 Mobile 시안을 비교하면서 시작한다. 화면 폭에 따라 열을 줄이고, 메뉴를 접고, 글자 크기를 조정하면 작업이 끝난 것처럼 보인다.

하지만 서비스를 운영하기 시작하면 시안에 없던 조건이 계속 등장한다. 사용자가 브라우저를 확대하고, 예상보다 긴 문자열이 들어오며, 다국어 번역으로 버튼의 길이가 달라진다. 데이터가 많은 표를 작은 화면에서 보여줘야 하고, 고정된 너비와 높이 때문에 설명이나 오류 메시지가 잘리기도 한다.

결국 반응형 웹의 목표는 특정 기기에서 화면을 비슷하게 만드는 것이 아니다. **콘텐츠와 기능이 다양한 환경에서도 사라지거나 깨지지 않도록 만드는 것**에 가깝다. 이 글에서는 반응형 UI를 구현하고 운영할 때 확인할 일곱 가지 기준을 정리한다.

## 1. Breakpoint는 디바이스가 아니라 콘텐츠가 결정한다

`768px`, `1024px`처럼 익숙한 숫자를 먼저 정하고 화면을 끼워 맞추기 쉽다. 하지만 같은 폭에서도 콘텐츠의 종류와 길이에 따라 레이아웃이 깨지는 지점은 달라진다.

Breakpoint는 다음 질문으로 결정하는 편이 안정적이다.

- 내비게이션 항목이 한 줄에 더 이상 들어가지 않는가?
- 폼의 Label과 Input을 나란히 배치했을 때 읽기 어려운가?
- 카드의 최소 너비를 유지할 수 있는가?
- 본문 한 줄이 지나치게 길거나 짧아지는가?

가능하다면 고정된 화면 구간을 늘리기보다 콘텐츠가 스스로 재배치되게 만든다.

```css
.card-list {
  display: flex;
  flex-wrap: wrap;
  gap: 1rem;
}

.card-list__item {
  min-width: 0;
  flex: 1 1 18rem;
}
```

`flex-basis`를 카드가 읽기 좋은 최소 너비로 정하고 줄바꿈을 허용하면, 공간이 충분할 때는 여러 열로 표시되고 부족할 때는 자연스럽게 다음 줄로 이동한다. 이는 “Tablet에서는 두 열”이라는 기기 중심 규칙보다 콘텐츠가 유지될 수 있는지를 기준으로 한 접근에 가깝다.

## 2. 작은 화면의 Table은 무조건 Card로 바꾸지 않는다

업무 시스템에서는 검색 결과와 통계 데이터를 Table로 표현하는 경우가 많다. 작은 화면에서 모든 행을 Card로 바꾸면 보기에는 단순해질 수 있지만, 행과 열의 관계를 비교하기 어려워지고 동일한 Label이 반복되어 화면이 길어진다.

먼저 데이터의 사용 목적을 구분해야 한다.

- 여러 행의 값을 비교해야 한다면 Table 구조를 유지한다.
- 한 항목의 상세 내용을 읽는 것이 중요하다면 Card 전환을 검토한다.
- 중요도가 낮은 열은 숨기기 전에 다른 경로로 확인할 수 있는지 점검한다.
- 가로 스크롤이 필요하다면 Table 영역에만 제한한다.

```html
<div class="table-scroll" role="region" aria-label="주문 목록" tabindex="0">
  <table>
    <!-- caption, thead, tbody를 포함한 실제 표 구조 -->
  </table>
</div>
```

```css
.table-scroll {
  max-width: 100%;
  overflow-x: auto;
  overscroll-behavior-inline: contain;
}

.table-scroll table {
  min-width: 48rem;
}
```

WCAG의 Reflow 기준에서도 데이터 표처럼 이차원 관계가 중요한 콘텐츠는 예외가 될 수 있다. 다만 표 바깥의 페이지 전체가 가로로 움직이거나, 개별 셀의 내용을 확인할 수 없는 상태가 되어서는 안 된다.

## 3. 긴 문자열은 예외가 아니라 정상 데이터로 취급한다

개발 환경에서는 `홍길동`, `상품명`, `example.com`처럼 짧은 값으로 화면을 확인한다. 운영 환경에서는 긴 회사명, 영문 상품명, 이메일, URL, 파일명, 오류 메시지가 들어온다.

Flexbox 내부에서 문자열이 영역을 밀어내는 문제는 `min-width: 0`을 빠뜨려 발생하는 경우가 많다.

```css
.result-item {
  display: flex;
  gap: 1rem;
}

.result-item__content {
  min-width: 0;
}

.result-item__title {
  overflow-wrap: anywhere;
}
```

말줄임표는 레이아웃을 지키는 쉬운 방법이지만 중요한 정보를 감출 수 있다. 전체 내용을 확인할 수 있는 상세 화면, 펼치기 기능, 접근 가능한 설명이 없다면 무조건적인 `text-overflow: ellipsis` 사용은 피하는 것이 좋다.

다국어를 지원한다면 번역 결과가 원문보다 길어진다는 전제로 버튼과 메뉴를 확인해야 한다. 텍스트 길이를 고정값으로 생각하지 않는 것이 핵심이다.

## 4. Mobile 화면뿐 아니라 확대와 Reflow를 확인한다

반응형 테스트를 브라우저의 Mobile Device Mode로만 끝내면 화면 확대 문제를 놓칠 수 있다. 사용자는 Desktop 화면을 200% 또는 400%로 확대하거나 운영체제의 글자 크기를 변경할 수 있다.

W3C WCAG 2.2의 Reflow 기준은 세로로 읽는 콘텐츠가 **320 CSS pixel에 해당하는 폭에서도 정보나 기능 손실 없이 표시**되는 것을 목표로 한다. 따라서 다음 항목을 함께 확인한다.

- 본문을 읽기 위해 가로와 세로를 동시에 스크롤해야 하는가?
- 고정 Header나 Footer가 확대된 화면의 대부분을 가리는가?
- 고정 높이 때문에 버튼이나 설명 문구가 잘리는가?
- 화면이 한 열로 바뀌어도 원래 기능에 접근할 수 있는가?

특히 `height`로 콘텐츠 영역을 고정하거나 `position: fixed` 요소를 많이 사용하면 확대 환경에서 문제가 쉽게 발생한다. 고정값이 필요한 이유가 없다면 `min-height`와 자연스러운 문서 흐름을 우선한다.

## 5. 키보드와 Focus 순서도 함께 반응해야 한다

화면에서 요소의 위치만 바꾸고 DOM 순서를 그대로 두면 시각적 순서와 키보드 탐색 순서가 달라질 수 있다. CSS `order`를 사용하거나 Desktop 요소와 Mobile 요소를 각각 만들어 숨기는 방식에서 자주 생긴다.

확인할 내용은 단순하다.

1. `Tab` 키로 화면의 모든 기능에 접근할 수 있는가?
2. Focus 이동 순서가 화면을 읽는 순서와 일치하는가?
3. 접힌 메뉴를 열었을 때 Focus가 메뉴 내부로 자연스럽게 이동하는가?
4. 메뉴를 닫으면 Focus가 메뉴를 열었던 버튼으로 돌아오는가?
5. Focus 표시가 배경과 충분히 구분되는가?

화면 크기에 따라 기능을 숨겨야 한다면 `display: none`만 적용하기 전에 그 기능을 대체할 경로가 있는지 확인해야 한다. 반응형 UI는 기능을 제거하는 작업이 아니라 작은 공간에 맞게 접근 경로를 다시 설계하는 작업이다.

## 6. 고정 너비와 높이는 필요한 영역에만 사용한다

시안의 크기를 그대로 옮기기 위해 `width`와 `height`를 고정하면 처음에는 화면을 맞추기 쉽다. 하지만 실제 데이터가 들어오거나 글자가 확대되면 콘텐츠가 잘리고, 작은 화면에서는 페이지 전체에 가로 스크롤이 생길 수 있다.

고정 크기를 사용하기 전에 다음 기준을 확인한다.

- 콘텐츠 길이가 달라져도 반드시 같은 높이를 유지해야 하는가?
- 고정 너비 대신 `max-width`로 상한만 정할 수 있는가?
- 고정 높이 대신 `min-height`로 최소 크기만 보장할 수 있는가?
- 가로 스크롤이 필요한 경우 해당 영역에만 제한되어 있는가?
- Flexbox 자식에 `min-width: 0`이 필요한가?

페이지의 기본 Container는 화면에 맞게 줄어들면서 큰 화면에서만 최대 너비를 제한하는 방식이 다루기 쉽다.

```css
.page-container {
  width: min(100% - 2rem, 72rem);
  margin-inline: auto;
}

.form-row {
  display: flex;
  align-items: flex-start;
  gap: 0.75rem 1rem;
}

.form-row__label {
  flex: 0 0 10rem;
}

.form-row__control {
  min-width: 0;
  flex: 1 1 auto;
}

@media (max-width: 40rem) {
  .form-row {
    flex-direction: column;
  }

  .form-row__label {
    flex-basis: auto;
  }
}
```

높이가 고정된 Card나 Form에 안내 문구와 오류 메시지가 추가되면 하단 버튼이 밀리거나 겹칠 수 있다. 콘텐츠가 늘어날 수 있는 영역은 문서 흐름에 따라 자연스럽게 커지도록 두고, 정말 필요한 내부 영역만 `overflow`로 제어하는 편이 안전하다.

`overflow: hidden`으로 깨진 부분을 감추는 것은 해결이 아니다. 어떤 콘텐츠가 넘쳤는지 확인하고, 줄바꿈·최소 너비·배치 방식 중 원인에 맞는 규칙을 적용해야 한다.

## 7. 실제 기기와 Cross-browser 회귀 테스트를 남긴다

브라우저 개발자 도구는 빠른 확인에 유용하지만 실제 기기의 주소 표시줄, 가상 키보드, Safe Area, 터치 스크롤까지 모두 재현하지는 못한다. 자동화 테스트와 수동 테스트의 역할을 나눠 운영하는 편이 현실적이다.

### 자동으로 확인할 항목

- 주요 Breakpoint별 Screenshot 회귀 테스트
- 페이지 전체의 가로 Overflow 발생 여부
- 핵심 기능의 키보드 접근과 접근성 검사
- 주요 화면의 Core Web Vitals 변화

### 직접 확인할 항목

- 실제 iOS Safari와 Android Chrome
- 화면 회전 전후의 레이아웃과 입력값 유지
- 가상 키보드가 열린 상태의 Form과 고정 버튼
- 긴 콘텐츠와 오류 메시지가 추가된 상태의 높이와 Overflow
- 브라우저 확대와 운영체제 글자 크기 변경

모든 기기와 브라우저를 동일하게 테스트할 수는 없다. 서비스의 실제 사용자 환경과 장애 이력을 바탕으로 지원 범위를 정하고, 문제가 발생할 때마다 테스트 항목을 보완하는 방식이 지속 가능하다.

## 마무리: 반응형 UI 검토 체크리스트

- [ ] Breakpoint가 기기 이름이 아니라 콘텐츠가 깨지는 지점을 기준으로 정해졌는가?
- [ ] 320px 수준의 좁은 폭과 화면 확대에서 페이지 전체 가로 스크롤이 발생하지 않는가?
- [ ] 긴 한글·영문·숫자·URL·다국어 문구를 넣어 보았는가?
- [ ] Table의 비교 기능과 Header-Cell 관계가 유지되는가?
- [ ] 키보드 Focus 순서가 시각적 순서와 일치하는가?
- [ ] 고정 너비·높이 때문에 콘텐츠가 잘리거나 겹치지 않는가?
- [ ] 실제 기기와 주요 브라우저에서 핵심 흐름을 확인했는가?
- [ ] 숨기거나 축소한 기능을 다른 경로로 사용할 수 있는가?

반응형 웹의 완성도는 시안과 같은 모양에서 결정되지 않는다. 예상하지 못한 콘텐츠와 사용 환경에서도 정보와 기능을 유지할 수 있는지가 더 중요한 기준이다.
