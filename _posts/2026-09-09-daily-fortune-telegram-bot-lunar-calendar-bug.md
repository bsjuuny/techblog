[davids_FortuneBot](https://t.me/davids_FortuneBot)은 텔레그램에서 이름과 생년월일시를 등록하면, 만세력으로 사주팔자를 계산해 보여주고 매일 아침 7시 30분에 오늘의 운세·바이오리듬을 보내주는 개인용 봇이다. 무료이고, 오락·자기성찰용이라고 명시하며 결과를 보장하지 않는다.

이 글에서 다루고 싶은 건 기능 자체보다, **완성해뒀다고 생각한 코드를 두 개의 AI 코딩 에이전트에게 독립적으로 감사시켰더니 실제로 몇 달째 있던 버그가 나온 경험**이다.

## 구조

세 저장소로 나뉜다.

```text
fortune-telegram   텔레그램 봇 진입점 (bot.py: 등록 대화, send_daily.py: 발송)
daily-fortune      오늘의 운세 텍스트·오행 분석 엔진 (로컬 Ollama 우선, 실패 시 템플릿)
manseryeok         사주(만세력) 계산 엔진 — 음력·윤달 변환, 사주팔자, 암호화 DB 저장
```

발송은 scheduler 프로젝트가 세 단계로 나눠 돌린다.

1. **03:00 `fortune-pregenerate`** — 오늘자 운세 문구를 발송 없이 캐시에만 채운다. 가장 느린 작업(Ollama 생성, 명당 약 16초)을 발송 마감 압박에서 떼어내는 게 목적이다.
2. **05:00 `fortune-retry-templates`** — 새벽에 Ollama가 실패해 템플릿으로 남은 사람만 골라 재시도한다.
3. **07:30 `fortune-daily`** — 대부분 캐시 히트로 즉시 발송, 캐시 미스만 그 자리에서 즉석 생성한다.

등록 직후에는 다음날 아침까지 기다리지 않고 그 자리에서 바로 발송한다.

## 이번에 한 것: 코드를 AI 코딩 에이전트 둘에게 감사시켰다

이 프로젝트는 몇 달 전에 만들어 잘 돌아가고 있다고 생각했다. 그런데 다른 프로젝트(위치 기반 재난 알림 봇)에서 [Codex CLI와 Grok Build CLI를 각각 read-only 샌드박스로 돌려 코드를 직접 읽고 검증시켰더니 실제 버그가 나온 경험](/project/automation/risk-alert-bot-location-based-weather-disaster-notifications/)이 있어서, 같은 방식을 이 프로젝트에도 적용했다.

두 에이전트에게 똑같은 질문을 던졌다 — "배경 설명이 실제 코드와 일치하는가, 개인정보·나이제한이 실제로 강제되는가, 계산 로직에 버그가 있는가." 서로 다른 모델이 독립적으로 저장소를 읽게 하면, 한쪽이 놓친 걸 다른 쪽이 잡아주는 경우가 실제로 있었다.

### 1. 음력 가입자의 바이오리듬·생일이 몇 주씩 틀리고 있었다

두 에이전트가 공통으로 지적했다. DB 스키마 주석에는 `birth_datetime -- 원본 입력 그대로 (양력 기준 ISO), 참고용`이라고 **양력으로 저장한다는 의도**가 분명히 적혀 있었는데, 실제 등록 코드는 사용자가 음력을 선택하면 **음력 원본 날짜를 그대로** 저장하고 있었다. 사주팔자 계산(`compute_saju`) 자체는 음력 입력을 올바르게 반영해서 맞게 나왔지만, 매일 발송되는 바이오리듬과 생일 축하 로직은 이 `birth_datetime` 컬럼을 그대로 양력처럼 읽어서 썼다.

```python
solar_birth = dt.date.fromisoformat(saju["solar_date"])
solar_birth_dt = dt.datetime.combine(solar_birth, birth_dt.time())
insert_person(conn, session["name"], solar_birth_dt, is_lunar, saju, chat_id=chat_id)
```

실제로 테스트해보니 체감이 컸다. 1990년 음력 4월 18일로 등록하면 실제 양력 생일은 5월 12일인데, 수정 전에는 4월 18일을 그대로 양력으로 써서 **바이오리듬 기준일이 24일이나 어긋나 있었다.** 코드 리뷰만으로는 "그럴듯해 보이는" 코드였는데, 실제 값을 계산해서 대조하니 바로 드러났다.

같은 흐름에서 **음력 윤달을 묻지 않는 문제**도 나왔다. CLI 등록 스크립트(`add_person.py`)에는 `--leap-month` 옵션이 있어 엔진 자체는 윤달을 지원하는데, 정작 봇의 대화형 등록 흐름에는 이 질문이 없었다. 음력을 선택했을 때만 윤달 여부를 한 번 더 묻는 단계를 추가했다.

### 2. "완전 삭제"가 완전하지 않을 수 있었다

`/delete`는 사람 레코드와 운세 캐시를 함께 지운다고 안내하는데, 실제 구현은 `chat_id`로 **가장 최근 레코드 하나**를 찾아 그 레코드의 캐시만 지우고 있었다. 봇 자체의 재등록 흐름은 매번 재등록 전에 기존 데이터를 먼저 지우기 때문에 평소엔 레코드가 중복될 일이 없지만, 관리용 CLI 스크립트로 같은 `chat_id`에 두 번째 레코드를 만들면 첫 번째 레코드의 캐시가 고아로 남을 수 있는 구조였다. "완전 삭제"라고 안내하는 이상, 그 chat_id에 걸린 모든 레코드의 캐시를 지우도록 고쳤다.

```python
person_ids = [row["id"] for row in
              conn.execute("SELECT id FROM people WHERE chat_id = ?", (str(chat_id),)).fetchall()]
for person_id in person_ids:
    delete_fortune_cache_by_person_id(conn, person_id)
```

### 3. 이름을 HTML 이스케이프 없이 그대로 넣고 있었다

Telegram 메시지를 `parse_mode: HTML`로 보내면서, 사용자가 직접 입력하는 이름을 이스케이프 없이 그대로 문자열에 끼워 넣고 있었다. 이름에 `<`나 `&` 같은 문자가 들어가면 메시지 포맷이 깨지거나 전송 자체가 실패할 수 있는 구조였다. `html.escape()`를 붙이는 걸로 끝나는 간단한 수정인데, 두 에이전트 중 하나(Grok)만 짚어낸 항목이었다 — 같은 코드를 봐도 무엇을 문제로 보는지는 에이전트마다 달랐다.

### 4. 개인정보 고지 문구가 헷갈리게 쓰여 있었다

"생년월일시 원본은 텔레그램으로 전송하지 않습니다"라는 문구가 있었는데, 이건 원래 "봇이 내보내는 발송 메시지에 생년월일시를 포함하지 않는다"는 뜻으로 쓴 거였다. 그런데 사용자가 애초에 생년월일시를 **입력하는 행위 자체가 텔레그램을 통해 이뤄진다**는 걸 생각하면, 문구만 보고는 "입력 자체가 텔레그램을 거치지 않는다"로 오해할 여지가 있었다. 무슨 뜻인지는 코드를 보면 명확했지만, 개인정보 고지문은 코드를 안 보고 문장만 읽는 사람 기준으로 써야 한다는 걸 다시 확인했다. 범위를 명확히 하는 쪽으로 문구를 고쳤다.

## 두 에이전트를 같이 쓴 이유

한쪽만 썼으면 놓쳤을 항목이 실제로 있었다 — HTML 이스케이프는 Grok만, "07:30 자동발송이 실제로 동작하는지"에 대한 의심은 Codex만 제기했다(이건 조사 범위에 scheduler 저장소가 빠져 있어서 생긴 오해였고, 확인해보니 실제로는 정상 등록돼 있었다). 서로 다른 모델에게 같은 저장소를 read-only로 읽게 하고 결과를 대조하는 게, 한 에이전트에게 두 번 물어보는 것보다 실질적으로 다른 관점을 준다는 걸 이번에도 느꼈다.

다만 두 에이전트 모두 근거 없는 추측을 답으로 내놓지는 않았다 — 확인 안 된 건 "확인되지 않음"이라고 명시했고, 실제로 코드를 인용하면서 주장했다. 이게 없었으면 지적사항을 하나하나 코드로 재검증하는 데 시간이 더 걸렸을 것이다.

## 남은 과제

- 출생 시각을 모르면 정오로 대입하는데, 등록 화면의 오행 분포에는 이 임의의 시주가 그대로 포함된다. 일일 운세 계산에는 영향 없지만, 시간 미상일 때는 오행 분포에서 시주를 빼는 게 더 정확할 것 같다.
- 동의는 강제되지만 동의한 시각·내용 자체는 DB에 남지 않는다. 진행을 막는 것과 감사 로그를 남기는 것은 다른 문제다.
- 날짜 입력 검증이 느슨해서 `1990-01-01 12:00 abc`처럼 뒤에 불필요한 문자가 붙어도 통과한다.
