{: .notice--info}

공모주(IPO) 청약 정보를 보여주는 개인 프로젝트 [ipo-master](https://github.com/bsjuuny/ipo-master)에는 한동안 `/admin` 페이지가 있었다. 자동 수집이 막힌 경쟁률 데이터를 수동으로 보정해 넣기 위한 페이지였는데, 여기 숨겨둔 토큰 세 개가 5개월 동안 배포된 사이트의 공개 JS 파일에 그대로 실려 있었다. 누구든 devtools를 열어 파일 하나만 읽으면 꺼내갈 수 있는 상태였다.

패치 하나하나는 그 순간엔 다 말이 됐다. 그런데도 결과적으로는 GitHub Personal Access Token이 실제로 유출돼 폐기(revoke)까지 해야 했다. 어쩌다 이렇게 됐는지 커밋 기록을 순서대로 따라가 봤다.

## 처음엔 평범한 기능이었다

`/admin` 페이지의 원래 역할은 간단했다. 로그인하면 GitHub Contents API를 직접 호출해서 `competition_override.json` 파일을 읽고 쓰는 것. 브라우저가 파일을 직접 쓰다 보니, 그러려면 브라우저가 GitHub에 쓸 수 있는 권한(Personal Access Token)을 들고 있어야 했다. 이 시점부터 이미 위험한 전제가 하나 깔린 셈이지만, 로그인 게이트가 있으니 "일단은 괜찮다"고 넘어갔다.

## 2단계 인증을 추가했다가, 27분 만에 뒤집었다

며칠 뒤 비밀번호만으로는 부족하다고 판단해 Google Authenticator 방식의 TOTP 2FA를 추가했다. 이때는 구조가 정상적이었다 — `/api/auth`라는 서버 라우트를 만들어서, 비밀번호와 TOTP 코드를 서버에서만 검증했다(`otplib.verifySync`). 시크릿 값은 서버 환경변수에만 있고 브라우저로는 한 번도 나가지 않는, 교과서적인 구조였다.

문제는 27분 뒤에 드러났다. 이 사이트는 Cafe24에 정적 파일로 배포되는 구조라, 애초에 서버 라우트(`/api/auth`) 자체가 프로덕션에서 동작하지 않았다. 로컬 개발 서버에서만 되고 실제 배포본에서는 로그인이 막히는 상황이었던 것이다.

여기서 "그럼 검증을 브라우저에서 직접 하자"로 방향을 틀었다. 이 결정 하나가 이후 모든 문제의 출발점이 됐다.

## 클라이언트에서 검증하려면, "정답"도 클라이언트에 있어야 한다

브라우저가 스스로 "이 비밀번호가 맞는지, 이 TOTP 코드가 맞는지"를 판단하려면, 비교 대상이 되는 정답값(비밀번호, TOTP 시크릿)도 브라우저 코드 안에 있어야 한다. 이때 쓴 방법이 Next.js의 `NEXT_PUBLIC_` 환경변수였다.

```js
const ADMIN_KEY = process.env.NEXT_PUBLIC_ADMIN_KEY ?? '';
const TOTP_SECRET = process.env.NEXT_PUBLIC_TOTP_SECRET ?? '';
```

Next.js에서 `NEXT_PUBLIC_` 접두사가 붙은 환경변수는 서버 전용 비밀 저장소가 아니라, **빌드 시점에 값이 그대로 클라이언트 JS 파일 안에 텍스트로 박히는** 기능이다. 프론트엔드 코드에서 API 엔드포인트 주소나 공개 설정값을 편하게 쓰라고 있는 것이지, 인증 정보를 위한 게 아니다. 이 접두사를 붙이는 순간 "비밀"이 아니라 "공개"가 된다.

로그인 검증 로직 자체도 그저 이 정도였다.

```js
if (input !== ADMIN_KEY) {
  setAuthError('비밀번호가 올바르지 않습니다.');
  return;
}
```

정답이 이미 같은 파일 안에 있으니, 이 코드는 사실상 자물쇠가 아니라 자물쇠 그림이었다.

## 막힐 때마다 한 겹씩 더 얹었다

여기서 끝이 아니었다. TOTP 검증에 브라우저의 `crypto.subtle`(WebCrypto) API를 썼는데, 이 API는 HTTPS 같은 보안 컨텍스트에서만 동작한다. 배포 환경에서 또 막히자, TOTP 알고리즘(HMAC-SHA1 기반 6자리 코드 생성)을 아예 순수 JavaScript로 손수 구현해서 우회했다. 이후에도 빌드 환경에 시크릿을 추가로 넣고 FTP 로그인 설정을 손보는 식의 패치가 몇 차례 더 이어졌다.

돌아보면 각 패치는 그 순간의 에러 메시지에 대한 합리적인 대응이었다. "정적 호스팅이라 API 라우트가 안 됨" → 클라이언트로 이동. "WebCrypto가 HTTPS를 요구함" → 직접 구현으로 우회. 매번 눈앞의 에러는 사라졌지만, 그때마다 "애초에 브라우저가 이 값을 몰라야 하는 것 아닌가"라는 더 근본적인 질문은 아무도 다시 던지지 않았다.

## 5개월 뒤에야 발견했다

3월 25일 이 구조가 자리 잡은 뒤로, 8월 31일 다시 들여다보기 전까지 약 5개월 동안 GitHub Personal Access Token, 관리자 비밀번호, TOTP 시크릿 세 개가 전부 배포된 사이트의 공개 JS 번들 안에 그대로 있었다. devtools의 Sources 탭에서 파일 하나를 열면 셋 다 평문으로 보이는 상태였다. 이 중 GitHub PAT은 실제로 유출된 것으로 확인돼 별도로 폐기해야 했다.

## 진짜 질문은 "어떻게 옮기나"가 아니라 "이 기능이 왜 필요한가"였다

다시 코드를 보면서 던진 질문은 "그럼 토큰만 서버로 옮기면 되나"가 아니라 "브라우저가 애초에 GitHub에 직접 써야 하는 이유가 있나"였다. 배포 파이프라인을 확인해보니 답이 이미 있었다 — `deploy-override.yml`이라는 GitHub Actions 워크플로가 `competition_override.json` 파일 변경을 감지해서, git push만 하면 자동으로 빌드·배포되는 구조가 이미 존재하고 있었다.

즉 브라우저에서 GitHub API로 파일을 직접 쓰는 기능은, 이미 있는 안전한 경로(로컬에서 파일 수정 → git push → CI가 자동 배포)와 결과적으로 똑같은 일을 하기 위해 굳이 위험을 감수하며 만든 중복 경로였다. 토큰 위치만 옮기는 건 절반짜리 해법이고, 진짜 해법은 이 기능 자체를 없애는 것이었다.

`/admin` 페이지(로그인 게이트와 GitHub API 읽기/쓰기 로직 558줄)를 통째로 삭제하고, 그 자리를 로컬에서만 실행하는 인터랙티브 CLI 스크립트(`scripts/edit-override.mjs`)로 대체했다. 이 스크립트는 디스크 위의 JSON 파일을 직접 수정하고, 원하면 git add/commit/push까지 대신 실행해준다. 개발자 본인이 이미 인증된 로컬 git 세션을 그대로 쓰기 때문에 별도 토큰이 필요 없다. 배포 워크플로 두 곳에서 `NEXT_PUBLIC_ADMIN_KEY` · `NEXT_PUBLIC_GITHUB_TOKEN` · `NEXT_PUBLIC_TOTP_SECRET`을 전부 걷어내고, 더는 쓰지 않는 `otplib` 의존성도 함께 정리했다.

## 남는 것들

- **`NEXT_PUBLIC_` 접두사는 "편의 기능"이 아니라 "공개 선언"이다.** 인증 정보·API 키·시크릿에는 절대 붙이면 안 된다. 이 규칙 하나만 처음부터 지켰어도 이번 유출은 없었다.
- **패치가 쌓이면 전제가 무너진다.** 개별 패치는 매번 그 순간의 에러에 대한 합리적인 대응이었지만, 그 합리성이 쌓이면서 "인증"이라는 기능의 근본 전제(정답은 서버만 안다) 자체가 조용히 무너지고 있었다. 에러가 사라졌다고 넘어가지 말고, 우회할 때마다 "원래 하려던 게 여전히 유효한가"를 한 번씩 다시 물어야 했다.
- **AI 페어 프로그래밍은 "되게 만드는 법"은 잘 찾는다.** 이 패치들 대부분은 Claude와 함께, 배포를 빨리 되게 만들려는 압박 속에서 만들어졌다. "이 방법으로 빌드가 통과한다"와 "이 방법이 안전하다"는 서로 다른 질문이고, 후자는 결국 사람이 시간을 두고 따로 다시 던져야 하는 질문이었다.
- **가장 안전한 코드는 지운 코드다.** 결국 문제를 없앤 건 더 나은 인증 방식이 아니라, 이미 있던 안전한 배포 경로를 알아채고 기능 자체를 삭제한 것이었다.
