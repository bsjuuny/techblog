> **배포 안내**  
> BizRadar는 아직 공개 URL로 서비스 중이 아닙니다. 이 글은 로컬 개발 환경에서 검증한 아키텍처와 구현 판단을 정리한 것이며, 실제 운영 서비스로 소개하는 글이 아닙니다.
{: .notice--warning}

BizRadar는 5~50인 규모 IT/SI 회사가 나라장터 공공 IT 입찰과 정부 지원사업을 찾고, 자기 회사 조건과 얼마나 맞는지 점수로 확인할 수 있게 만든 B2B SaaS MVP다. 개인 사이드 프로젝트지만 실제 서비스처럼 인증·RLS·테스트·CI 기준을 갖추고 만들었고, 그 과정에서 내린 판단들이 프런트엔드 업무에서도 그대로 쓸 만해서 정리해 둔다.

## 구조: 웹과 워커를 완전히 분리했다

```text
브라우저 → Railway(Next.js) → Supabase(Postgres + Auth, RLS)
로컬 PC → PM2 → Python 워커 → 공공 API(나라장터 등) → Ollama → Supabase
```

웹 앱과 워커는 서로를 직접 호출하지 않는다. 둘 다 Supabase 하나만 공유한다. 워커가 분석 결과를 쓰고, 웹 앱은 그걸 읽기만 한다.

**왜 이렇게 나눴는가.** AI 분석에 쓰는 Ollama(`qwen3.5:9b`)는 GPU 호스팅 비용을 피하려고 로컬 PC에서만 돌린다. Railway가 절대 Ollama를 직접 호출하지 않게 만들어 두면, 로컬 Ollama가 꺼져도 그건 로컬 사고일 뿐 Railway 장애로 번지지 않는다. 실제로 헬스체크 엔드포인트(`/api/health`)도 의도적으로 Ollama 상태를 체크하지 않는다 — 체크해 버리면 로컬 프로세스 상태가 배포 서비스의 헬스 상태를 오염시키기 때문이다.

## 판단 기준이 필요했던 부분

### 1. 매칭 점수는 LLM이 아니라 규칙 엔진으로 만들었다

회사 조건과 공고가 얼마나 맞는지 보여주는 Match Score는 배점표 기반 결정론적 계산이다: 업종 20점(정확 매칭 실패 시 키워드 퍼지 매칭으로 대체), 예산 15점, 경력 15점, 자격요건 10점(부분 인정 없음 — 필수 자격증 하나라도 없으면 그 조건은 0점), 지역 5점, 일정 5점(마감까지 7일 이상이면 만점).

LLM 호출로도 만들 수 있었지만, 대시보드를 열 때마다 나오는 매칭 점수가 매번 조금씩 달라지거나 왜 이 점수가 나왔는지 설명이 안 되면 신뢰할 수 없는 기능이 된다. 그래서 이 부분만큼은 재현 가능하고 설명 가능한 규칙 엔진으로 남겨뒀다. AI는 "이 공고가 IT 관련인지, 어떤 기술스택을 요구하는지" 같은 원문 해석에만 쓰고, 최종 점수 계산에는 관여하지 않는다.

### 2. 공공데이터포털 API에서 실제로 겪은 문제 두 가지

나라장터(G2B) 수집기를 만들면서 겪은, 문서만 봐서는 알기 어려웠던 두 가지가 있다.

- API 경로에 `ad/` 세그먼트가 빠지면 404가 아니라 "서비스가 존재하지 않습니다"라는 일반 에러가 뜬다. 경로 자체를 의심하기보다 인증 문제로 오해하기 쉬운 에러 메시지였다.
- data.go.kr이 발급하는 서비스 키는 이미 URL 인코딩된 상태다. `httpx`의 파라미터 인코딩이나 `curl --data-urlencode`를 그대로 쓰면 이중 인코딩이 되고, 그러면 "등록되지 않은 서비스 키"라는 오해하기 쉬운 에러로 인증이 실패한다. 인코딩된 값을 그대로 URL에 붙이는 방식으로 우회했다.

두 경우 모두 에러 메시지가 실제 원인을 가리키지 않아서, 처음엔 잘못된 방향(인증 정보 재발급 등)으로 시간을 썼다. 이후 이 두 가지를 트러블슈팅 문서에 먼저 적어두고, 다음에 같은 함정에 안 빠지게 했다.

### 3. 응답 형식이 문서와 다를 수 있다는 전제로 파서를 짰다

수집기의 응답 파서는 스키마 누락, JSON이 아닌 응답(HTML 에러 페이지가 실제로 온다), 레거시 에러 포맷(`OpenAPI_ServiceResponse`)까지 전부 크래시 없이 처리하게 만들었다. 공공 API는 장애 시 API 문서에 없는 형태의 응답을 주는 경우가 실제로 있어서, "정상 스키마만 온다"는 전제로 짜면 수집 파이프라인이 새벽에 조용히 멈춰 있는 일이 생긴다.

### 4. 테스트 정책: 실패하는 테스트를 통과시키려고 테스트를 건드리지 않는다

`docs/TESTING.md`에 명시한 원칙이 두 가지 있다 — 테스트를 초록으로 만들려고 테스트를 건너뛰지 않는다, RLS를 꺼서 테스트를 통과시키지 않는다. 실제로 PostgREST가 `timestamptz` 컬럼을 자동 파싱된 값이 아니라 문자열로 반환한다는 걸 테스트 중에 발견했는데(`bid_close_at` 날짜 계산이 `str`/`datetime` 뺄셈으로 크래시), 테스트를 손대는 대신 명시적으로 `datetime.fromisoformat()` 파싱을 추가해서 실제 코드를 고쳤다.

## 남은 과제

- 아직 공개 배포 전이다. 현재는 웹(Railway)·워커(로컬 PC, PM2) 모두 개발 환경 기준으로 검증된 상태다.
- BizInfo·K-Startup 수집기 등 G2B 이후 단계는 `docs/MVP_SCOPE.md`의 단계 계획대로 진행 중이다.
