## PHP2Shell 사태, AI가 40년 묵은 기술부채를 드러내다

IEEE Spectrum이 다룬 PHP2Shell 취약점은 2024년에 이미 보고됐던 PHP의 out-of-memory 버그가 출발점입니다. 원래는 크래시만 일으키는 수준이라 방치됐는데, OpenAI가 후원한 보안 업체 Calif가 AI 도구를 동원해 2주 만에 이 버그를 임의 코드 실행으로 격상시켰습니다. 공격 대상에는 NASA, 위키피디아, 백악관 사이트를 포함해 WordPress·Drupal 기반 사이트 전체가 들어갑니다.

다행히 화이트해커가 먼저 찾아 패치가 먼저 나왔지만, 기사 속 Columbia대 Suman Jana 교수의 말이 핵심입니다. 메모리를 어디서 어떻게 덮어써야 하는지 알아내는 건 "로켓 과학은 아니고, 그냥 고통스러울 만큼 세밀한 추론"이라는 겁니다. AI가 바로 그 세밀한 추론을 잘한다는 뜻이고, 이건 공격자와 방어자 모두에게 똑같이 적용됩니다.
(https://spectrum.ieee.org/ai-in-cybersecurity-php2shell-vulnerability)

실무적으로는 두 가지를 챙겨야 합니다. 오래된 의존성이나 레거시 C/PHP 코드베이스를 쓰고 있다면 지금까지 "크래시만 나는 버그"로 방치한 이슈 목록을 다시 들여다볼 때입니다.

그리고 Anthropic이 10월 22일 공개한 것처럼, 패치를 LLM이 생성하고 그 패치의 정합성 증명도 LLM이 만들되 증명 검증기만 사람이 다루는 포멀 베리피케이션 조합이 앞으로 표준적인 패치 파이프라인이 될 가능성이 높습니다.

## RTX Spark에서 Linux 쓰면 추론 속도가 왜 반토막 나는가

MindStudio 벤치마크에 따르면 Nvidia RTX Spark 노트북(MSI Prestige 기준)에서 GPT-OSS-120B를 돌렸을 때 Windows는 초당 65.4토큰, WSL은 65.1토큰이 나왔는데 네이티브 Linux는 13.9토큰에 그쳤습니다. 전원을 연결한 상태에서만 이 차이가 벌어지고, 배터리로 구동하면 Linux도 Windows와 비슷한 수준까지 올라온다는 점이 특이합니다.

원인은 GPU 드라이버가 아니라 Nvidia Platform Controllers and Framework라는 Windows 전용 펌웨어 컴포넌트입니다. 이게 CPU·GPU 간 전력 배분 테이블을 쥐고 있는데, 이 테이블이 암호화돼 있어 Windows 드라이버만 복호화할 수 있습니다.

Linux에서는 GPU 클록이 전원 연결 시 약 780MHz로 고정되고, 이는 Windows의 2.2GHz와 비교해 세 배 가까이 차이가 납니다.

로컬 LLM용으로 이런 유니파이드 메모리 노트북을 검토 중이라면 참고할 선택지는 이렇습니다.

- 네이티브 Linux 듀얼부팅: GPU 가속은 동작하지만 전원 연결 시 추론 속도가 5분의 1 수준으로 떨어짐
- WSL: Windows 드라이버 스택을 그대로 쓰기 때문에 네이티브 Windows와 거의 동일한 성능, 다만 기본 메모리 할당 14GB를 수동으로 늘려야 함
- Windows 네이티브: 가장 빠르지만 vLLM, SGLang 같은 Linux 중심 AI 툴체인과 궁합이 떨어짐

당분간은 WSL이 현실적인 절충안이고, 근본 해결은 Nvidia가 전력 관리 로직을 Linux 드라이버에 포팅해야 가능합니다.
(https://www.mindstudio.ai/blog/linux-nvidia-rtx-spark-laptop)

## GitHub 장애, PR·이슈·Git 오퍼레이션이 동시에 흔들렸다

GitHub 공식 상태 페이지에 따르면 11월 4일 09시 49분(UTC)부터 Git Operations, API Requests, Issues, Pull Requests, Actions 전반에서 장애가 발생했고, 11시 50분에 해결됐습니다. 약 두 시간 동안 PR 생성이나 git push 같은 기본 작업이 지연되거나 실패했다는 뜻입니다.

상태 페이지 업데이트 흐름을 보면 처음엔 Git Operations·Issues·Pull Requests로 시작해서 API Requests, Actions까지 영향 범위가 점점 넓어졌습니다. 근본 원인 분석은 아직 공개되지 않았습니다.

CI/CD 파이프라인을 GitHub Actions에 의존하는 팀이라면 이런 장애가 배포 타이밍과 겹칠 때의 대응 절차를 미리 정해두는 게 낫습니다. 자세한 원인은 추후 공개될 포스트모템을 확인하면 됩니다.
(https://www.githubstatus.com/incidents/smtdswd1h2w4)

## 검증 가능한 답과 "이해"는 다른 문제인가

이 글은 과학의 "가치중립 이상"이 냉전 이후 만들어진 사회적 계약의 산물이라고 짚으면서, 검증과 지식을 동일시하는 태도가 왜 위험한지 설명합니다. 페르마의 마지막 정리가 중요해진 과정도 예로 듭니다. 증명 자체보다 그 증명이 모듈러성 정리와 어떻게 연결되는지, 동료 심사가 어떻게 오류를 걸러냈는지가 더 중요했다는 겁니다.

AI 코딩 도구에 익숙한 개발자라면 이 논의가 낯설지 않을 겁니다. LLM이 내놓은 패치나 설계가 테스트를 통과해도, 그걸 설명하지 못하는 팀원만 남으면 나중에 디버깅할 사람이 없는 것과 같은 구조입니다. 검증된 결과와 팀이 실제로 이해하고 있는 결과 사이의 간극을 어떻게 메울지는 코드 리뷰 문화 차원에서도 고민해볼 만한 주제입니다.
