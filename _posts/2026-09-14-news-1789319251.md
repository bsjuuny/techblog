# 오늘의 기술 뉴스 브리핑

오늘은 하드웨어 해킹부터 저수준 x86 아키텍처 트리비아, GPU 생태계 이야기까지 폭넓은 소식이 올라왔습니다. 특히 "직접 뜯어보고 직접 다시 만든다"는 해커 정신이 돋보이는 항목들이 많았습니다. 개발자 관점에서 실무에 바로 도움이 될 만한 것부터 순수하게 재미있는 것까지 골라봤습니다.

**JetKVM Mini** (https://jetkvm.com/blog/introducing-jetkvm-mini)
$33부터 시작하는 유선/무선 KVM 오버 IP 기기로, 오픈소스 펌웨어와 기존과 동일한 웹 인터페이스를 유지한다고 합니다.
원격 서버나 홈랩을 운영하는 개발자에게 KVM 오버 IP는 원격지 장비의 BIOS 화면까지 제어할 수 있게 해주는 필수템인데, 기존 상용 제품들은 수십만 원대가 흔했습니다.
이 가격대에 오픈소스 펌웨어까지 결합된다면 홈랩·엣지 서버 관리 방식에 실질적인 변화를 줄 수 있습니다.
구체적인 하드웨어 스펙이나 무선 구현 방식은 원문 참고가 필요합니다.

**CUDA for AMD on Windows** (https://github.com/Speedstu/CUDA-for-AMD-Windows)
ZLUDA와 ROCm/HIP을 조합해 CUDA 대상으로 짜인 Windows 애플리케이션을 AMD GPU에서 돌리는 프로젝트입니다.
CUDA는 사실상 GPU 연산 생태계의 표준 언어이고, 이 때문에 AMD 카드를 가진 사람들은 딥러닝·과학 연산 도구를 쓸 때마다 벽에 부딪혀왔습니다.
ZLUDA는 원래 인텔 GPU용으로 시작했다가 AMD 쪽으로 옮겨간 프로젝트로 알려져 있는데, 이런 호환 레이어가 계속 살아남는다는 건 엔비디아 종속에서 벗어나려는 수요가 여전히 크다는 뜻입니다.
다만 라이선스·성능·안정성 이슈가 늘 따라다니는 영역이라 실무 도입 전에는 검증이 필요합니다.

**Why is the x86 undefined instruction called ud2? Why 2?** (https://devblogs.microsoft.com/oldnewthing/20260910-00/?p=112689)
ud0, ud1 다음에 ud2가 왔다는 짧은 설명이 붙어 있습니다.
Raymond Chen의 Old New Thing 블로그는 윈도우/x86 내부 동작의 역사적 배경을 파고드는 걸로 유명한데, 이런 사소해 보이는 명명 규칙 뒤에는 보통 하위 호환성이나 인텔의 내부 정치가 얽혀 있는 경우가 많습니다.
컴파일러나 디버거를 다루는 개발자라면 ud2가 의도적으로 프로그램을 크래시시키는 데 쓰이는 명령어라는 걸 알고 있을 텐데, 그 이름의 유래를 아는 건 단순 트리비아 이상으로 저수준 시스템의 역사를 이해하는 데 도움이 됩니다.
자세한 내막은 원문에서 확인하는 게 좋습니다.

**Reverse engineering my e-scooter and rewriting the firmware in Rust** (https://bensimms.moe/reverse-engineering-scooter/)
Egret GT 전동 킥보드의 하드웨어와 펌웨어를 리버스 엔지니어링하고, 디스플레이 유닛용 커스텀 펌웨어를 Rust로 작성한 과정을 다룹니다.
IoT 기기 내부 통신 프로토콜을 분석하고 직접 침투해 들어가는 과정은 임베디드 개발자들에게 실전 교과서 같은 사례입니다.
특히 요즘 임베디드 영역에서 C/C++를 대체하려는 Rust의 실사용 사례가 계속 쌓이고 있다는 점도 눈여겨볼 만합니다.
제조사가 막아놓은 기기를 사용자가 직접 뜯어 고친다는 서사 자체도 우측한 소비자 권리(Right to Repair) 논의와 맞닿아 있습니다.

**Libraries Run Rust Inside Python (With PyO3)** (https://belderbos.dev/blog/how-libraries-run-rust-inside-python/)
PyO3로 Rust JSON 파서를 Python 모듈로 빌드하고, Rust 데이터가 Python dict/list로 변환될 때 드는 비용을 실측한 글입니다.
Python의 성능 병목을 Rust/C로 우회하는 건 NumPy 시절부터 이어진 전통적 해법이지만, PyO3는 그 과정을 훨씬 안전하고 간결하게 만들어준 도구로 평가받습니다.
다만 이 글이 짚듯 언어 경계를 넘나들 때 발생하는 직렬화·변환 비용은 공짜가 아니며, 이걸 무시하면 오히려 순수 Python보다 느려지는 함정에 빠지기 쉽습니다.
polars, pydantic-core처럼 실제 프로덕션에서 PyO3를 쓰는 라이브러리가 늘고 있다는 점에서 이 벤치마크 감각은 실무에 바로 적용할 수 있습니다.
