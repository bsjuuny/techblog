# hr-chatbot 파이프라인 굳히기: travel-chatbot에서 이식한 보안·안정성 패치기

## admin1234, 이대로 둘 순 없었다

hr-chatbot의 admin 페이지 인증 코드를 다시 들여다보다가 admin1234라는 하드코딩된 폴백 비밀번호가 그대로 남아있는 걸 발견했다. 게다가 /api/docs 쓰기 엔드포인트는 인증 자체가 아예 없는 상태였다. 예전에 travel-chatbot에서 이미 같은 문제를 겪고 고쳐둔 기억이 나서, 그 해결책을 hr-chatbot에도 그대로 이식하기로 했다.

adminAuth.js를 새로 만들어 세션 쿠키 기반 인증으로 바꾸고, 비밀번호 비교는 timingSafeEqual로 처리했다. 로그인 시도에는 rate limiting을 걸어 무차별 대입을 막았고, /api/docs 쓰기 요청에도 인증을 필수로 걸었다.

## 스트리밍 중 끊기면 답변이 통째로 날아간다

/api/chat은 SSE로 토큰을 스트리밍하는 구조인데, 중간에 연결이 끊기면 지금까지 생성된 답변이 그냥 사라지는 문제가 있었다. 게다가 AI_MODE=search로 설정했을 때는 애초에 어댑터가 토큰 스트리밍을 하지 않아서 화면에 답변이 아예 안 뜨는 문제도 함께 있었다.

원인은 서버 쪽에 진행 중인 스트림을 재개할 방법이 없었다는 점이었다. 그래서 streamStore.js로 진행 중인 답변을 서버 메모리에 붙잡아두고, /api/chat/resume 라우트를 새로 추가해서 재연결 시 이어받을 수 있게 했다. sse.js와 sseClient.js로 SSE 송수신 로직을 정리하면서 하트비트 코멘트도 넣어 프록시의 idle timeout으로 연결이 끊기는 것도 막았다. 이 작업 과정에서 search 모드가 스트리밍을 안 한다는 사실도 같이 드러나서, 답변이 뜨도록 로직을 손봤다.

## 요청 본문 검증이 없어서 뭐든 들어올 수 있었다

/api/chat, /api/auth, /api/feedback, 그리고 admin 로그인 요청까지 공통적으로 본문 크기 제한이나 history/message 검증이 빠져 있었다. 누구든 과도하게 큰 요청이나 이상한 형태의 데이터를 보낼 수 있는 구조였다.

readBody.js와 limits.js를 추가해서 요청 본문 크기 제한과 유효성 검사를 공통 로직으로 뽑아냈다. 이 두 파일을 각 라우트에 붙여 넣는 식으로 적용 범위를 넓혔다. 저장되는 답변과 피드백도 DB에 넣기 전에 안전한 길이로 잘라내도록 손봤다.

## IP당 요청 제한도 빠져 있었다

claude/openai 모드는 API 비용, ollama 모드는 로컬 GPU 부하 문제로 이어질 수 있는데, 정작 요청량을 제어할 장치가 없었다. 누군가 반복 요청을 보내면 그대로 비용이나 부하로 이어지는 구조였다.

rateLimit.js를 새로 만들어 파일 기반으로 IP별·일별 채팅 요청 횟수를 제한했다. clientIp.js로 클라이언트 IP를 뽑아내는 로직을 분리해서 rate limiting에 재사용했다. 이 모든 변경사항은 travel-chatbot에서 검증된 패턴을 hr-chatbot 구조에 맞게 옮긴 것이라, 큰 시행착오 없이 빠르게 적용할 수 있었다.
