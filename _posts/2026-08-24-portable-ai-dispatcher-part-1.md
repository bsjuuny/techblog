> **AI 활용 안내**  
> 이 글은 작성자의 설계와 구현 경험을 바탕으로 AI와 함께 초안을 작성하고 문장을 다듬었습니다. 최종 내용과 공개 여부는 작성자가 직접 확인했습니다.
{: .notice--info}

> **개발 상태 안내**  
> Portable AI Dispatcher는 현재 개발 중인 프로젝트다. 포터블 키트 생성, 실행 스크립트, 하드웨어 사전 점검과 주요 안전장치는 구현되어 있지만, 여러 사양의 실제 PC와 USB 환경을 이용한 종단 간 검증은 계속 진행하고 있다. 이 글은 완성된 제품의 사용 설명서가 아니라, 지금까지의 설계 판단과 구현 상태를 기록한 개발기다.
{: .notice--warning}

AI 코딩 도구를 사용하는 환경에는 보통 몇 가지 전제가 있다. 인터넷에 연결되어 있고, Node.js나 Git을 설치할 수 있으며, 필요하면 패키지와 모델을 내려받을 수 있다는 전제다. 개인 개발 PC에서는 자연스럽지만, 외부망을 사용할 수 없거나 프로그램 설치 권한이 제한된 PC에서는 이 전제부터 성립하지 않는다.

이번에 만들고 있는 **Portable AI Dispatcher**는 여기서 출발했다.

> 인터넷이 끊긴 Windows PC에 USB 하나를 연결했을 때, 별도 설치 없이 로컬 AI가 기존 프로젝트를 읽고 제한된 범위의 코드를 수정하게 만들 수 있을까?

단순히 GGUF 모델 파일을 USB에 복사하는 것만으로는 해결되지 않았다. 모델을 실행할 런타임, Dispatcher를 실행할 Node.js, 변경을 격리할 Git, PC 사양에 맞는 모델 선택, 무결성 확인과 실패 처리까지 전부 함께 움직여야 했다.

이 글은 3부작 중 1부다. 이번 글에서는 **AI가 실행될 기반을 어떻게 이동 가능한 형태로 만들었는지**를 다룬다. 2부에서는 로컬 LLM에 셸 권한을 주지 않고 파일을 수정하게 만든 코딩 루프를, 3부에서는 변경 사항을 검증하고 실제 저장소에 반영하는 안전장치를 정리할 예정이다.

## 먼저 포터블의 범위를 정했다

처음에는 "실행 파일과 모델을 USB에 넣으면 되지 않을까"라고 생각하기 쉽다. 하지만 목표 환경을 구체적으로 적어 보니 포터블이라는 말에 포함되어야 할 조건이 많았다.

- 대상 PC는 인터넷에 연결되어 있지 않을 수 있다.
- Node.js와 Git이 설치되어 있다고 가정할 수 없다.
- 관리자 권한이나 전역 패키지 설치 권한이 없을 수 있다.
- USB 드라이브 문자는 PC마다 달라질 수 있다.
- GPU가 없더라도 CPU만으로 최소 기능이 동작해야 한다.
- 모델과 런타임은 실행 중 자동으로 다운로드하면 안 된다.
- 작업 기록은 USB가 아니라 실제 프로젝트 폴더에 남아야 한다.

마지막 조건도 중요했다. 모델과 실행 파일은 USB에서 읽더라도, 어떤 작업을 실행했고 무엇이 변경됐는지에 대한 기록은 프로젝트에 귀속되어야 한다. USB를 다른 PC로 옮겼다고 해서 서로 다른 프로젝트의 기록이 한곳에 섞이면 감사 로그와 문제 재현이 어려워진다.

그래서 포터블 키트와 작업 프로젝트의 책임을 다음처럼 분리했다.

```text
USB: portable-ai-dispatcher/
├─ app/         # 빌드된 Dispatcher
├─ bin/         # 실행·사전 점검 스크립트
├─ config/      # 포터블 환경의 보수적인 기본 설정
├─ runtime/     # Node.js, MinGit, 로컬 LLM 런타임
├─ models/      # 사전에 검증해 둔 GGUF 모델 팩
└─ templates/   # 선택 사항인 오프라인 프로젝트 템플릿

PC: 작업할-project/
├─ src/
├─ package.json
├─ .git/
└─ .dispatcher/ # 작업 이력, 감사 로그, 실패 기록
```

USB는 실행에 필요한 자산을 제공하고, 현재 터미널의 프로젝트 폴더는 작업 대상과 기록을 소유한다. 런처는 `AI_DISPATCHER_PORTABLE_ROOT`를 통해 모델과 런타임의 기준 경로만 USB로 고정하고, 현재 작업 디렉터리는 바꾸지 않는다.

## 설치 프로그램 대신 완성된 폴더를 만든다

폐쇄망에서 실행할 도구가 시작하자마자 `npm install`이나 모델 다운로드를 요구한다면 포터블이라고 보기 어렵다. 그래서 `portable assemble` 명령은 네트워크 설치를 수행하지 않는다. 현재 빌드 결과와 미리 준비된 자산을 하나의 폴더로 복사할 뿐이다.

```text
ai-dispatcher portable assemble <destination>
```

이 과정에서 포함하는 항목은 다음과 같다.

- 의존성을 번들에 포함한 `dist` 애플리케이션
- Windows용 Node.js 22 이상 실행 파일
- 포터블 MinGit
- 검토한 llama.cpp 런타임
- 사전에 내려받고 검증한 GGUF 모델 팩
- 포터블 기본 설정과 `.cmd` 실행 스크립트

필수 자산이 없다고 몰래 다운로드하거나 빈 파일을 정상 자산처럼 취급하지 않는다. 대신 누락된 위치에 안내 파일을 만들고, 조립 결과에 사용 전 준비해야 할 항목을 명시한다. 대상 폴더가 이미 존재하면 덮어쓰지 않고 중단하도록 했다. 포터블 키트 조립이 기존 결과물을 조용히 훼손하지 않게 하기 위해서다.

Node.js도 시스템에 설치하지 않는다. 실행 스크립트는 USB 안의 `runtime/node/node.exe`로 빌드된 CLI를 직접 실행한다. Dispatcher 런처는 USB에 MinGit이 있으면 해당 경로를 PATH 앞에 연결해 격리 작업에서 사용할 Git을 확실히 지정한다. 별도로 등록할 수 있는 전역 `git` shim은 시스템에 정식 Git이 있으면 그것을 우선하고, 없을 때만 USB의 MinGit으로 대체한다.

Git을 필수로 포함한 이유는 단순히 버전 관리를 편하게 하기 위해서가 아니다. Dispatcher는 코드 변경 작업을 원본 폴더에서 바로 실행하지 않고 별도의 Git worktree에 격리한다. Git이 없으면 이 안전 경계를 만들 수 없으므로, 폐쇄망 환경에서는 선택 의존성이 아니라 실행 조건이다.

## USB 드라이브 문자는 믿지 않는다

Windows에서 같은 USB가 항상 `E:`로 연결된다는 보장은 없다. 다른 PC에서는 `F:`나 `G:`가 될 수 있고, 이미 연결된 디스크에 따라 같은 PC에서도 문자가 달라진다. 따라서 설정 파일에 절대 경로를 저장하면 포터블 키트가 처음 사용한 PC에 묶인다.

런처는 자신의 위치인 `%~dp0`를 기준으로 키트 루트를 계산한다. 전역 명령을 선택적으로 등록한 경우에도 특정 드라이브 문자를 기억하지 않고, 연결된 드라이브에서 `portable-ai-dispatcher/portable-kit.json`을 찾아 현재 위치를 다시 결정한다.

프로젝트 폴더에서 실행하는 흐름은 다음과 같다.

```text
작업 프로젝트에서 ai-dispatcher 실행
            ↓
현재 연결된 USB 키트 위치 확인
            ↓
USB의 Node.js·Git·설정·모델 경로 연결
            ↓
현재 프로젝트를 작업 디렉터리로 유지한 채 실행
```

전역 명령 등록은 필수가 아니다. USB의 `bin/ai-dispatcher.cmd`를 직접 실행할 수도 있고, 자주 사용하는 PC에서만 명령 shim을 등록할 수도 있다. 이 shim도 USB가 분리되어 있으면 명확한 오류를 출력하고 종료한다.

## 처음 보는 PC에서는 실행보다 진단이 먼저다

포터블 키트가 어느 PC에서나 같은 모델을 무조건 실행하게 하는 것은 안전하지 않다. 메모리가 부족할 수 있고, CPU가 런타임에서 요구하는 AVX2를 지원하지 않을 수도 있다. 이 경우 단순한 성능 저하가 아니라 프로세스가 `Illegal Instruction`으로 바로 종료될 수 있다.

그래서 실제 모델 서버를 시작하기 전에 `preflight`가 환경을 확인한다.

```text
bin\preflight.cmd
```

현재 점검하는 대상은 다음과 같다.

1. CPU 모델, 논리 코어 수와 사용 가능한 명령어 집합
2. 전체 메모리와 사용 가능한 메모리
3. CUDA·Vulkan 등 사용 가능한 가속 경로
4. 호환되는 로컬 런타임과 실행 파일의 무결성
5. Git 사용 가능 여부
6. 모델 팩의 메타데이터, 라이선스 정보와 해시
7. 현재 장비에 모델이 실제로 적재 가능한지 여부

점검 결과를 바탕으로 장비를 `CPU_LITE`, `CPU_STANDARD`, `CPU_PLUS`, `GPU_STANDARD`, `AI_WORKSTATION`으로 나누고, CUDA → Vulkan → CPU 순으로 사용할 수 있는 런타임을 고른다. 다만 GPU를 찾지 못했다고 해서 실패시키지는 않는다. CPU 경로를 기본 안전망으로 유지하는 것이 목표다.

CPU 명령어 집합을 확실하게 판별하지 못한 경우에는 AVX나 AVX2 전용 바이너리를 낙관적으로 선택하지 않는다. 느리더라도 일반 CPU용 런타임만 허용한다. 포터블 환경에서는 최고 성능보다 **모르는 장비에서 예측 가능하게 실패하거나 동작하는 것**이 더 중요하다고 판단했다.

결과는 세 가지 상태로 표현한다.

- `READY`: 필수 런타임, Git과 사용 가능한 모델이 모두 준비된 상태
- `LIMITED`: 일부 기능은 사용할 수 있지만 포터블 기준을 완전히 충족하지 못한 상태
- `NOT_READY`: 실행 전에 해결해야 할 필수 조건이 있는 상태

폐쇄망용 키트에서는 조건이 부족한데도 사용 가능한 것처럼 넘어가지 않는다. `offlineKitRequired` 설정이 켜진 경우 CPU 기본 런타임, Git, 호환 모델 중 하나라도 준비되지 않으면 `NOT_READY`다.

## 모델은 큰 것 하나보다 장비별 팩으로 나눴다

현재 포터블 기본 구성은 메모리 16GB 환경과 32GB 환경을 나누어 생각하고 있다.

```text
16GB PC → Qwen2.5-Coder 7B 계열 양자화 모델
32GB PC → Qwen2.5-Coder 14B 계열 양자화 모델
```

모델 파일만 놓는 것이 아니라 `model-pack.json`에 모델 ID, 파일명, 최소 메모리, 권장 컨텍스트 크기, 라이선스 메타데이터와 SHA-256을 함께 둔다. 런타임도 같은 방식으로 manifest를 사용한다. 파일 이름이 그럴듯하다는 이유만으로 실행하지 않고, 현재 하드웨어와 선언된 조건이 맞는지 확인하기 위해서다.

여기서 중요한 현실적인 한계가 있다. CPU에서 14B 모델을 실행하는 것은 클라우드 코딩 도구와 체감 속도가 크게 다르다. 새 프로젝트 전체를 한 번에 만들어 달라는 개방형 요청은 오래 걸리고 결과도 불안정하다. 현재 테스트에서도 빈 프로젝트를 크게 구성하게 하는 작업보다, 이미 구조가 잡힌 저장소에서 파일 몇 개를 수정하는 좁은 작업이 훨씬 현실적이었다.

따라서 포터블 버전의 목표를 "어떤 개발 작업이든 대신하는 오프라인 개발자"로 잡지 않았다. 우선은 다음 범위를 안정적으로 만드는 데 집중한다.

- 기존 코드 탐색과 설명
- 오류 원인이 비교적 명확한 수정
- 파일 수가 적은 기능 추가
- 문서와 설정의 제한적인 변경
- 변경 후 기존 build·lint·test 실행

모델 크기와 실행시간, 작업 성공률은 실제 장비별 검증이 더 쌓인 뒤 수치로 정리할 예정이다.

## 현재 어디까지 만들었나

현재 구현된 범위는 다음과 같다.

- 빌드 결과, Node.js, Git, 런타임과 모델을 한 폴더로 조립하는 기능
- USB 상대 경로를 사용하는 Windows 실행 스크립트
- Dispatcher용 포터블 Git 연결과 시스템 Git을 우선하는 선택형 전역 shim
- CPU·메모리·가속기·런타임·모델 팩·Git 사전 점검
- 런타임과 모델 manifest 및 해시 검증
- 인터넷 다운로드가 없는 보수적인 포터블 기본 설정
- 포터블 자산과 프로젝트 작업 기록의 경로 분리
- 조립 결과와 누락 자산을 확인하는 단위 테스트

반면 아직 완료됐다고 말하지 않는 부분도 분명하다.

- 서로 다른 세대와 사양의 Windows PC에서 반복한 호환성 검증
- 실제 USB 파일시스템과 장시간 실행에서의 안정성 확인
- 포터블 구성에 포함할 llama.cpp 바이너리의 실기 통합 검증
- 7B·14B 모델별 작업 유형, 처리시간과 메모리 사용량 측정
- 모델 배포 라이선스와 해시가 포함된 최종 모델 팩 확정
- `preflight → 모델 서버 → 코드 수정 → 검증 → 반영` 전체 시나리오 반복 테스트

즉, 폴더를 만드는 기능은 동작하지만 "USB를 아무 PC에 꽂아도 바로 쓸 수 있다"고 선언하기에는 아직 검증해야 할 조합이 남아 있다. 이 차이를 숨기지 않고 기록하는 것이 이번 개발기의 목적이기도 하다.

## 다음 글: 로컬 LLM에 셸을 주지 않는 이유

실행 환경을 옮기는 것만으로 AI 코딩 도구가 완성되지는 않는다. llama.cpp나 Ollama의 completion API는 텍스트를 생성할 뿐, 스스로 프로젝트 파일을 읽거나 수정하지 못한다. 그렇다고 모델이 생성한 셸 명령을 그대로 실행하게 하면 포터블 환경의 안전 경계가 너무 넓어진다.

2부에서는 모델이 매 턴 하나의 구조화된 action만 선택하게 하고, Dispatcher가 파일 목록·읽기·검색·정확 치환·쓰기를 대신 수행하도록 만든 과정을 다룰 예정이다. 경로 탈출, 읽지 않은 파일 덮어쓰기, 같은 변경의 무한 반복을 어떻게 막았는지도 함께 정리한다.

Portable AI Dispatcher는 아직 진행 중이다. 완성된 결과만 나중에 정리하기보다, 어떤 제약을 발견했고 그 제약 때문에 설계가 어떻게 바뀌었는지를 단계별로 남겨보려 한다.
