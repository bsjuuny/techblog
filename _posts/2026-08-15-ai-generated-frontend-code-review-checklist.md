> **AI 활용 안내**  
> 이 글은 작성자의 주제 선택과 경험 검토를 바탕으로 AI와 함께 초안을 작성하고 문장을 다듬었습니다. 최종 내용과 공개 여부는 작성자가 직접 확인했습니다.
{: .notice--info}

AI 개발 도구는 코드 탐색, 반복 작업, 테스트 초안, 리팩터링 후보 제안에 유용하다. 설명만 입력해도 그럴듯한 Component와 Hook을 빠르게 만들 수 있다.

문제는 **그럴듯함과 정확함이 다르다는 것**이다. 코드는 문법적으로 자연스러워 보여도 요구사항을 잘못 이해할 수 있고, 존재하지 않는 API를 사용할 수 있다. 테스트를 통과시키기 위해 중요한 검증을 제거하거나, 기존 프로젝트의 상태 관리와 오류 처리 규칙을 무시할 수도 있다.

따라서 AI가 만든 코드를 검토할 때는 “코드가 실행되는가?”보다 넓은 질문이 필요하다.

> 이 변경이 올바른 문제를 해결하며, 기존 시스템 안에서 안전하게 운영될 수 있는가?

이 글에서는 AI가 생성하거나 수정한 Frontend 코드를 실무에 반영하기 전에 확인할 절차를 정리한다.

## 1. 먼저 AI에 맡길 작업의 경계를 정한다

AI는 작업 범위가 명확하고 결과를 검증하기 쉬울수록 유용하다.

### 맡기기 좋은 작업

- 반복적인 Type 정의와 데이터 변환 코드 초안
- 기존 Pattern을 따르는 Component 추가
- Test Case 후보와 Edge Case 목록 작성
- 이름 변경, 작은 함수 분리와 같은 제한된 Refactoring
- 오류 메시지 분석과 관련 코드 탐색
- 문서와 주석의 초안 작성

### 사람의 판단이 먼저 필요한 작업

- 결제, 인증, 권한처럼 실패 비용이 큰 업무 로직
- 개인정보와 고객 데이터 처리
- 전체 Architecture와 상태 관리 방식 결정
- 접근성, 법적 요구사항, 보안 정책 판단
- 오래된 시스템의 동작을 추론해야 하는 대규모 변경
- 외부 API나 Package 도입 결정

AI를 사용하지 말아야 한다는 뜻이 아니다. 위험한 작업일수록 AI에는 분석과 대안 제시를 맡기고, 결정과 적용 범위는 개발자가 통제해야 한다.

## 2. 코드보다 먼저 Context와 완료 조건을 전달한다

“검색 Component를 만들어 줘”라는 요청에는 중요한 정보가 빠져 있다. 검색 조건을 URL에 저장하는지, 기존 Form Library가 있는지, API 취소가 필요한지, 오류 메시지 규칙은 무엇인지 알 수 없다.

작업 요청에는 최소한 다음 내용을 포함하는 것이 좋다.

```text
목표: 주문 목록의 검색 조건을 URL Query와 동기화한다.

제약:
- 기존 Router와 Form Library를 유지한다.
- 새로운 Package를 추가하지 않는다.
- 검색 조건 변경 시 Page를 1로 초기화한다.
- 빠르게 연속 검색하면 이전 요청을 취소한다.

완료 조건:
- 새로고침 후에도 검색 조건이 유지된다.
- Loading, Empty, Error 상태가 구분된다.
- Keyboard만으로 검색과 초기화를 수행할 수 있다.
- 기존 Test와 Build가 통과한다.
```

프로젝트의 모든 파일을 무조건 전달하는 것도 좋은 방법은 아니다. 관련 문서, 기존 구현 예시, 변경 대상과 금지 영역을 선별해 제공한다. Context가 많다는 사실보다 **어떤 자료를 신뢰해야 하는지 명확한 것**이 중요하다.

## 3. 완성된 화면보다 Diff를 먼저 읽는다

화면이 정상적으로 보이면 내부 변경을 놓치기 쉽다. AI 도구가 파일 여러 개를 수정할 수 있다면 결과 화면을 보기 전에 Diff부터 확인한다.

검토 순서는 다음과 같이 단순하게 유지할 수 있다.

1. 예상한 파일만 변경됐는가?
2. 삭제되거나 비활성화된 Test가 있는가?
3. 새로운 Package와 설정 변경이 있는가?
4. 인증, 권한, API Endpoint가 바뀌었는가?
5. 요청하지 않은 “정리”나 대규모 Refactoring이 포함됐는가?
6. 되돌리기 어려운 데이터 변경이나 Script가 추가됐는가?

AI가 수정한 코드라고 해서 별도의 관대한 기준을 적용해서는 안 된다. 사람이 작성한 Pull Request와 같은 기준으로 검토하되, **범위 확장과 조용한 삭제**를 더 주의 깊게 본다.

## 4. API와 Dependency는 공식 출처에서 다시 확인한다

AI는 존재하지 않는 함수나 Package를 자연스럽게 제안할 수 있다. 실제로 존재하더라도 오래된 사용법, 다른 Major Version의 API, 유지보수가 중단된 Package일 수 있다.

새로운 Dependency가 추가된다면 다음 항목을 확인한다.

- Package Registry에 실제로 존재하는가?
- 공식 Repository와 배포 주체가 일치하는가?
- 현재 프로젝트의 Runtime과 Version을 지원하는가?
- 최근에도 유지보수되고 있는가?
- License가 프로젝트 정책과 맞는가?
- 이미 설치된 도구로 해결할 수 없는가?

API 사용법은 Blog나 AI의 설명만 믿지 않고 해당 Version의 공식 문서와 Release Note에서 확인한다. Package 이름이 그럴듯하다는 이유만으로 설치하지 않는 것이 Supply Chain 위험을 줄이는 가장 단순한 방법이다.

## 5. Build·Lint·Test를 증거로 남긴다

AI가 “검증했습니다”라고 설명하는 것과 실제 명령이 성공한 것은 다르다. 프로젝트가 제공하는 검증 명령을 직접 실행하고 결과를 확인한다.

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

프로젝트마다 명령은 다르지만 검증 층은 비슷하다.

- **Type Check:** 잘못된 데이터 구조와 함수 계약을 찾는다.
- **Lint/Static Analysis:** 코드 규칙과 잠재 오류를 확인한다.
- **Unit Test:** 분기와 순수 로직을 검증한다.
- **Integration/E2E Test:** 사용자 흐름과 API 연결을 확인한다.
- **Production Build:** 개발 환경에서 드러나지 않는 문제를 찾는다.

AI가 생성한 Test도 검토 대상이다. 구현 내용을 그대로 복사해 같은 가정을 반복하거나, 실패하는 Test를 삭제·Skip 처리하지 않았는지 확인한다. 좋은 Test는 현재 구현을 설명하는 데 그치지 않고 요구사항이 깨지는 것을 막아야 한다.

## 6. Frontend는 정상 상태보다 예외 상태를 더 확인한다

Type Check와 Unit Test가 통과해도 UI는 쉽게 실패한다. 특히 AI가 만든 예제는 정상 응답과 충분한 화면 폭을 전제로 하는 경우가 많다.

### 상태 검증

- 첫 Loading과 추가 Loading이 구분되는가?
- 결과가 0건일 때 Empty 상태가 표시되는가?
- Network 오류와 업무 오류가 구분되는가?
- 중복 클릭과 연속 요청이 제어되는가?
- Component가 Unmount된 뒤 응답이 도착해도 안전한가?
- 권한이 없거나 일부 데이터가 누락되어도 화면이 유지되는가?

### UI 검증

- 320~390px 폭에서 가로 Overflow가 발생하지 않는가?
- 긴 한글·영문·숫자·URL을 처리하는가?
- Keyboard 탐색 순서와 Focus 표시가 올바른가?
- Label, Button, Error Message가 보조기술에 전달되는가?
- 느린 Network에서 Layout Shift가 발생하지 않는가?

자동화할 수 있는 검증은 CI에 추가하고, 시각적·상호작용 판단이 필요한 항목은 수동 Checklist로 남긴다.

## 7. 민감한 정보는 입력 전에 차단한다

AI 도구에 전달할 수 있는 정보의 범위는 회사 정책과 사용 중인 서비스의 데이터 처리 조건에 따라 달라진다. 도구의 종류와 관계없이 다음 정보는 승인된 환경과 절차가 없다면 입력하지 않는 것이 기본이다.

- API Key, Access Token, Cookie와 인증정보
- 고객 이름, 연락처, 계정과 거래 데이터
- 공개되지 않은 Source Code와 업무 규칙
- 내부 URL, Server 정보와 보안 설정
- 장애 Log에 포함된 개인정보와 Session 정보
- 계약서, 기획서 등 외부 공개가 제한된 문서

필요하다면 샘플 데이터로 교체하고 식별 가능한 값은 마스킹한다. AI가 Repository나 외부 도구에 접근할 수 있다면 필요한 파일과 권한만 제공하고, 작업 후 실제 변경과 외부 전송 여부를 확인한다.

보안은 Prompt에 “민감정보를 노출하지 마”라고 쓰는 것만으로 해결되지 않는다. 입력 데이터 최소화, 권한 제한, 출력 검토가 함께 필요하다.

## 8. 변경을 작게 나누고 되돌릴 수 있게 만든다

AI에 큰 목표를 한 번에 맡기면 검토해야 할 변경도 커진다. 요구사항 분석, 구현, Test, 문서 변경을 작은 단계로 나누면 오류가 발생한 지점을 찾기 쉽다.

```text
1. 관련 코드와 현재 동작 분석
2. 변경 계획과 영향 파일 확인
3. 최소 구현
4. Test 추가 및 실행
5. UI·접근성 수동 검증
6. 문서와 최종 Diff 정리
```

각 단계에서 변경 파일과 결과를 확인하고, 한 Commit에는 하나의 목적만 담는다. AI가 빠르게 많은 코드를 만들 수 있다는 이유로 변경 규모까지 커질 필요는 없다.

## 9. 최종 판단과 책임은 개발자에게 남는다

AI는 구현 속도를 높일 수 있지만 업무의 우선순위, 위험 수준, 사용자의 불편을 스스로 책임지지 않는다. 다음 질문에 개발자가 답할 수 없다면 코드를 Merge하기 이르다.

- 왜 이 방법을 선택했는가?
- 어떤 대안을 검토했는가?
- 실패하면 어떤 사용자와 기능이 영향을 받는가?
- 문제가 발생했을 때 어떻게 감지하고 되돌릴 것인가?
- 이 코드가 기존 Architecture와 운영 규칙에 맞는가?

AI의 설명을 그대로 기록하기보다 실제로 확인한 근거를 Pull Request나 변경 문서에 남긴다. 도구가 아니라 팀이 결정을 재현할 수 있어야 한다.

## AI 생성 코드 검증 체크리스트

### 요구사항과 범위

- [ ] 변경 목적과 완료 조건이 명확한가?
- [ ] 요청하지 않은 파일이나 기능이 수정되지 않았는가?
- [ ] 기존 Architecture와 Coding Convention을 따르는가?

### 코드와 Dependency

- [ ] 전체 Diff를 직접 읽었는가?
- [ ] 삭제·Skip된 Test와 우회된 검증이 없는가?
- [ ] 새로운 API와 Package를 공식 출처에서 확인했는가?
- [ ] Version, 유지보수 상태, License를 확인했는가?

### 검증

- [ ] Type Check, Lint, Test, Production Build가 통과했는가?
- [ ] Loading, Empty, Error와 연속 요청을 확인했는가?
- [ ] Mobile, Keyboard, 접근성과 긴 문자열을 확인했는가?
- [ ] 실패 시 Rollback 방법이 있는가?

### 보안과 책임

- [ ] Prompt와 첨부 자료에 민감정보가 없는가?
- [ ] AI 도구에 필요한 최소 권한만 제공했는가?
- [ ] 변경 이유와 위험을 개발자가 설명할 수 있는가?
- [ ] 최종 결과를 사람이 승인했는가?

AI 개발 도구를 잘 사용한다는 것은 더 많은 코드를 생성하는 것이 아니다. **작업 범위를 통제하고, 결과를 증거로 검증하며, 최종 판단을 개발자가 유지하는 것**이 안정적인 활용에 더 가깝다.
