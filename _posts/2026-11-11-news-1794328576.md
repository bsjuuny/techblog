## Amazon은 왜 Sonnet 4.6을 결정 모델로 바꿨나

Amazon 내부 티켓 분류 시스템에서 Claude Sonnet 4.6을 쓰던 두 엔지니어가 Strands Decider라는 결정 모델로 교체해 비용을 98% 줄였습니다. 원문에 따르면 티켓당 비용이 $0.0222에서 약 $0.0005로 떨어졌고, 처리 시간도 평균 4,215ms에서 897ms로 줄었습니다. (https://strandsagents.com/blog/amazon-saves-millions-replacing-sonnet-with-strands-decider/)

결정 모델은 텍스트를 생성하지 않고, 주어진 선택지 중 하나에 확률과 신뢰도를 매깁니다. 티켓을 20개 카테고리 중 하나로 분류하는 작업처럼 '닫힌 선택지' 문제에 딱 맞는 구조입니다.

이 글에서 가장 실무적인 대목은 전환 방식입니다. BEDROCK/DUAL/DECIDER 세 가지 모드로 AppConfig 설정 하나만 바꿔가며 실 트래픽에서 두 모델을 동시에 돌려보고 불일치를 비교했습니다. 되돌리는 데 45초짜리 설정 변경이면 충분했다는 점이 눈에 띕니다.

다만 이 방식이 통한 이유는 분명합니다. 레이블 카탈로그가 고정돼 있고, 볼륨이 크고, 레이턴시가 중요한 경우에만 적용됩니다. 레이블마다 설명 텍스트가 필요하거나 카탈로그가 매주 바뀌는 작업이라면 LLM을 대체하기 어렵다고 원문도 명시하고 있습니다.

## AlphaProof Code, Signal 프로토콜을 수학적으로 증명하다

Google DeepMind가 AlphaProof Code라는 에이전트 프레임워크로 Signal 프로토콜의 실제 코드를 포멀 버리피케이션했다고 발표했습니다. Lean이라는 정리 증명 언어로 600만 줄 이상의 증명을 생성했고, 사람이 다시 봐야 했던 부분은 전체 코드베이스의 1%뿐이었다고 합니다. (https://deepmind.google/blog/introducing-alphaproof-code/)

포멀 버리피케이션은 원래 설계 단계에서 멈추는 경우가 많습니다. 설계와 실제 컴파일된 코드 사이의 간극에 진짜 취약점이 숨어 있는 경우가 많기 때문에, 이 작업이 코드 레벨까지 내려간 점이 핵심입니다.

검증 과정에 4주가 걸렸다는데, 원문은 이런 규모의 작업이 전통적으로 전문가 팀이 수년씩 걸리던 일이라고 설명합니다. 실제로 과거에 패치된 버그 두 개를 일부러 다시 심어서 테스트했더니 시스템이 해당 버전을 안전하지 않다고 증명해냈다는 대목도 검증 신뢰도를 보여주는 근거로 제시됐습니다.

개발자 입장에서는 암호 프로토콜 구현체의 포멀 버리피케이션이 AI 에이전트로 자동화 가능한 수준까지 왔다는 신호로 읽힙니다. 다만 이 결과가 다른 프로토콜이나 더 일반적인 코드베이스에 얼마나 일반화되는지는 이 글만으로는 확인되지 않습니다.

## 뉴욕 퀸즈 공공도서관, 랜섬웨어로 전자대출 중단

퀸즈 공공도서관이 랜섬웨어 공격을 받아 웹사이트, 모바일 앱, 디지털 미디어 서비스가 중단됐습니다. 다행히 와이파이와 대출/반납 기계, 7개 지점의 공용 PC는 복구됐다고 공지하고 있습니다. (https://connect.queenslibrary.org/)

공공 도서관처럼 예산이 빠듯한 공공기관의 인프라가 랜섬웨어 공격 대상이 되는 사례는 미국에서 드물지 않습니다. 도서관 시스템은 레거시 소프트웨어가 많고 보안 투자 우선순위가 낮은 경우가 흔해서, 이런 공격에 특히 취약한 편입니다.

개발자 입장에서 흥미로운 지점은 복구 전략입니다. 모든 걸 한꺼번에 내리는 대신 핵심 기능별로 단계적 복구 순서를 공지하고 있는데, 이는 장애 대응 커뮤니케이션의 한 사례로 참고할 만합니다. 자세한 공격 경로나 피해 규모는 이 공지만으로는 확인되지 않습니다.

## tar 아카이브 하나가 왜 8가지로 다르게 풀리는가

GNU tar 명령 한 번으로 만든 tarball 하나가 GNU tar, bsdtar, 7-Zip, Java Commons Compress, PHP, RubyGems, R, Haskell, .NET 등에서 전부 다른 결과를 내는 사례를 다룹니다. 핵심은 하드링크에 size 레코드를 끼워 넣는 pax 헤더 트릭입니다. (https://stoppels.ch/2026/11/07/the-hardest-tarball.html)

POSIX 스펙이 하드링크의 데이터 블록을 "포함될 수도 있다"는 식으로 애매하게 남겨둔 틈을 파고든 사례입니다. 그 결과 어떤 툴은 그 512바이트를 무시하고, 어떤 툴은 데이터로 읽고, 어떤 툴은 아예 헤더를 깨뜨립니다.

목록으로 정리하면 다음과 같습니다.

- GNU tar, BusyBox, Python, Go, Perl: size를 무시하고 정상적으로 세 파일을 추출
- bsdtar(macOS 기본 tar): 512바이트를 하드링크 데이터로 써버려 원본 파일 내용이 깨짐
- 7-Zip, node-tar, Rust tar 등: 데이터로 인식하지만 건너뛰어 empty 파일이 누락됨
- Java Commons Compress, PHP PharData, RubyGems, R: 각기 다른 방식으로 엉뚱한 파일/디렉터리를 생성
- .NET, Julia, uv의 tar-codec: 아예 아카이브를 거부

압축 포맷을 다루는 라이브러리를 직접 짜거나 신뢰해야 하는 입장이라면, 같은 포맷 스펙이라도 구현체마다 해석이 갈리는 지점이 실제로 존재한다는 걸 보여주는 좋은 사례입니다. 저자는 이런 사례 134개를 모은 테스트 스위트(haampie/tar-minefield)도 운영하고 있다고 밝히고 있습니다.

## 라즈베리파이4에 NetBSD 11 데스크톱 올리기

라즈베리파이4에 NetBSD 11을 설치하고 NsCDE 데스크톱 환경까지 올리는 과정을 담은 가이드입니다. UEFI 펌웨어 설치, WiFi 드라이버 수동 설정, pkgin 패키지 관리, X11과 ctwm, NsCDE 빌드까지 단계별로 다루고 있습니다. (https://neongd.com/articles/netbsd11-rpi4.gmi)

저자는 "AI 슬롭이 섞이지 않은 유일한 오픈소스 OS"라는 이유로 NetBSD를 택했다고 적고 있는데, 이건 저자 개인의 평가이지 검증된 사실은 아닙니다. 다만 BSD 계열이 라즈베리파이 같은 ARM 보드에서 주변기기 지원이 리눅스만큼 매끄럽지 않다는 건 잘 알려진 사실이고, 이 글의 WiFi 펌웨어 심볼릭 링크 트릭이 그 단면을 잘 보여줍니다.

실무에 바로 쓸 정보라기보다는, 레거시 유닉스 계열 OS를 저전력 보드에서 굴려보고 싶은 사람에게 실제로 따라 할 수 있는 체크리스트에 가깝습니다. 패키지명이나 설정 파일 경로가 구체적으로 나와 있어서 참고 가치는 있습니다.
