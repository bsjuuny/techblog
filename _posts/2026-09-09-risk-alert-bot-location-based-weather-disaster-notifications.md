[Risk Alert Bot](https://t.me/davids_riskAlertBot)은 텔레그램에서 위치를 최대 3곳(집·회사 등) 저장해두면, 그 지역의 실시간 날씨·1시간 예보·긴급재난문자를 조회하거나 자동으로 알림받는 개인용 봇이다. 서버 하나 없이 로컬 PC에서 PM2로 상시 구동하며, 기상청·카카오·행정안전부의 공공데이터 API만으로 동작한다.

이 글에서 다루고 싶은 건 봇 자체보다, 공공데이터 여러 개를 조합해 개인화된 알림을 만들 때 부딪힌 판단들이다.

## 문제: 범용 앱은 "내 동네" 기준으로 안 맞는다

날씨 앱, 재난문자, 기상특보는 이미 다 있다. 하지만 "내가 저장해둔 2~3곳에 한해서, 필요한 것만 골라서" 알려주는 서비스는 마땅한 게 없었다. 직접 만들기로 하면서 세운 원칙은 세 가지였다.

- 위치는 사용자가 직접 저장(GPS 공유 또는 주소 검색)한 곳만 다룬다 — 위치 추적이 아니다.
- 알림은 사용자가 물어봐야 답하는 게 아니라, 조건이 맞으면 먼저 보낸다(강수 시작 예측, 재난문자).
- 공공데이터 API 쿼터는 유한한 공유 자원이라는 전제로 설계한다.

## 구조

```text
사용자 위치 저장 → 카카오 좌표API로 행정동 확인 → 기상청 격자좌표로 변환 → 저장(JSON)
                                                              │
                        ┌─────────────────────────────────────┼─────────────────────────┐
                        ▼                                     ▼                         ▼
              초단기실황/예보(기상청)                   긴급재난문자(행안부)              사용자 조회(pull)
              30분 주기 폴링 → 강수 예측 시 push      5분 주기 폴링 → 지역 매칭 시 push   즉시 응답
```

핵심 모듈은 단순하다. `kmaGrid.mjs`가 위경도를 기상청 격자로 변환하고(Lambert Conformal Conic 투영), `kmaWeather.mjs`가 초단기실황·예보를 조회하고, `disasterMsg.mjs`가 오늘자 긴급재난문자를 가져온다. `bot.mjs`는 텔레그램 롱폴링으로 명령을 처리하고, `setInterval`로 두 개의 백그라운드 확인 루프(강수 예측, 재난문자)를 돌린다.

## 판단 기준이 필요했던 부분

### 1. "서울"과 "서울특별시"는 같은 지역이 아니다(코드 입장에서는)

카카오 좌표API는 시도명을 축약형("서울", "충남")으로 주는데, 행안부 재난문자 API의 수신지역명은 공식 전체 명칭("서울특별시", "충청남도")을 쓴다. 문제는 이게 단순 접미사 제거로 안 풀린다는 점이다 — "충남"은 "충청남도"의 접두사가 아니라, 가운데 글자("청")를 통째로 빼먹은 축약이다. 결국 시도 17개를 직접 매핑한 표를 만들어 해결했다.

```js
const SIDO_ROOTS = {
  충남: ['충청남', '충남'],
  전북: ['전라북', '전북'], // 2024년 전북특별자치도로 개칭된 이후도 함께 커버
  // ...
};
```

일반화된 규칙으로 풀릴 것 같은 문제가 실제로는 한국 행정구역 개편 이력(강원특별자치도, 전북특별자치도)까지 걸쳐 있어서, 억지로 규칙화하기보다 표로 명시하는 쪽이 더 정확하고 유지보수하기 쉬웠다.

### 2. API 쿼터는 "사용자 수"가 아니라 "격자 수"에 비례해야 한다

처음 구현은 요청이 올 때마다 기상청 API를 그대로 호출했다. 개인용일 때는 문제없지만, 화이트리스트를 풀어 공개 범위를 넓히기로 하면서 계산이 달라졌다 — 같은 동네 사용자 100명이 각자 날씨를 조회하면 API는 100번 불린다. 기상청 API 자체가 시간 단위로만 갱신되는데, 요청마다 새로 부르는 건 낭비다.

그래서 격자 좌표(nx, ny) 단위로 10분 캐시를 넣었다. 이러면 API 호출 횟수가 사용자 수가 아니라 "고유 격자 수"에 비례하게 된다 — 좁은 지역에 사용자가 몰릴수록 오히려 효율이 좋아지는 구조다.

```js
async function fetchCurrentWeatherRaw(nx, ny) {
  const cacheKey = `${nx},${ny}`;
  const cached = getCached(ncstCache, cacheKey);
  if (cached) return cached;
  // ... API 호출 후 캐시에 저장
}
```

### 3. 캐시를 넣으면서 "몇 분 전" 표기가 거짓말을 하게 됐다

캐시를 붙이자마자 드러난 부작용이 있었다. 관측 시각을 "9월 9일 08:00 (방금)"처럼 미리 문자열로 만들어 캐시에 저장해뒀더니, 캐시가 재사용되는 10분 동안 계속 "방금"이라고 표시됐다. 캐시된 건 API 원본 값이어야 하고, "몇 분 전"이라는 건 **조회 시점마다 다시 계산돼야 하는 값**이라는 걸 뒤늦게 깨달았다.

해결은 캐시에는 원본 관측 시각(Date 객체)만 저장하고, 사람이 읽는 형태로 바꾸는 포맷팅은 캐시 히트 여부와 무관하게 매번 실행하도록 분리하는 것이었다. 캐시할 데이터와 매 호출마다 재계산할 데이터를 섞으면 이런 종류의 미묘한 버그가 생긴다는 걸 다시 확인했다.

### 4. 공개 범위를 넓히기 전에 동의·삭제부터

처음엔 개인용으로만 쓸 생각이라 화이트리스트(허용 사용자 ID)만 걸어뒀다. 불특정 다수에게 공개하기로 방향을 바꾸면서, 위치 데이터를 동의 없이 수집하는 구조로는 안 된다고 판단해 기능을 추가하기 전에 먼저 막았다.

- `/start` 시 수집 항목·목적·보관 방식을 안내하고, 동의 버튼을 누르기 전까지는 위치 저장 자체가 안 되도록 모든 진입점(위치 공유, 주소 검색, 조회 명령)에 동의 확인을 넣었다.
- `/삭제` 한 번으로 위치·동의 기록을 전부 지울 수 있게 했다.

기능부터 만들고 나중에 약관을 붙이는 순서로 하면 결국 뒤늦게 전체 구조를 다시 손대야 한다. 처음부터 동의 게이트를 진입점에 박아두는 쪽이 코드도 더 단순했다.

## 남은 과제

- 그룹채팅에서 위치를 공유하는 경우는 고려하지 않았다 — 개인 대화(DM) 기준으로만 설계했다.
- 재난문자·강수 알림 상태는 메모리에만 있어서 봇을 재시작하면 초기화된다. 개인 규모에서는 재알림 한 번 더 가는 정도라 무해하지만, 사용자가 늘면 영속 저장으로 옮겨야 한다.
- 지금은 날씨·재난문자만 다루는데, 대기질(에어코리아)·산불 위험 같은 소스를 더 붙일 여지가 남아 있다.

공개 범위를 사용자 한 명에서 여러 명으로 넓히는 순간, "일단 되게 만들기"에서 "쿼터·동의·데이터 정리까지 감안한 설계"로 기준 자체가 달라진다는 걸 이번에 다시 확인했다.
